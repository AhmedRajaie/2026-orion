PART 06 / 07

Architect Your Algo
Like a Mini Company

A serious algo is not one giant script. It is a small organization with clear roles, responsibilities, and authority.

01 — WHY THIS MATTERS

Do Not Build One Giant Script

Part 5 showed that live trading needs more than a strategy. Part 6 is about how to organize the system so it can be tested, monitored, and fixed.

The beginner version of an algo is often one file that does everything: reads prices, calculates signals, places orders, tracks positions, and decides risk. That is fine for a toy example. It is not fine once real money, real data, and real execution are involved.

A better mental model is a mini company. Each part of the system has one job. Each job has clear boundaries. The risk function has authority. If something breaks, you know where to look.

A well-built algo is not clever because it is complicated.

It is safe because every component knows exactly what it is responsible for.
02 — THE MINI COMPANY

Five Roles Inside a Serious Algo

Think of the system as a small organization. Each role does one thing well.

Algo System Org Chart
01

02

Turns raw data into indicators, signals, and strategy inputs.
03

Places, cancels, and tracks orders with the broker.

05

Monitors limits and has authority to pause or shut down the system.
↳ The Risk Officer is not “one more feature.” In a serious system, the Risk Officer outranks everyone.
03 — ROLES

What Each Role Actually Does

The goal is separation of responsibility. One component should not secretly do another component’s job.

Data Agent
The source of truth
Ingests prices, volumes, corporate actions, and account data. It checks for missing candles, stale feeds, strange spikes, and whether the market is actually open.
Research Agent
The signal factory
Cleans and transforms data into signals: moving averages, volatility, momentum, mean reversion, filters, and anything else the strategy needs to make a decision.
Execution Agent
The order desk
Does not decide whether the idea is good. It receives an approved order instruction and handles the mechanics: place, cancel, retry, confirm, and reconcile.
Portfolio Manager
The capital allocator
Decides how much to commit, how many positions can coexist, whether the portfolio is overexposed, and whether new trades fit the existing book.
Risk Officer
The authority to stop
Checks position limits, daily loss, drawdown, abnormal fills, stale data, and broker errors. If the risk layer says stop, the rest of the system stops.
The Execution Agent should not invent trades.
The Research Agent should not place orders.
The Portfolio Manager should not ignore risk limits.

Each role has a job. That is the architecture.
04 — SYSTEM FLOW

How a Trade Moves Through the Company

The trade should pass through a controlled sequence before it reaches the market.

→

→

This order matters. The system should not send an order first and check risk afterward. It should not size a position without knowing current exposure. It should not trade on stale data. The architecture is the discipline.

↳ A good system makes the safe path the default path.
05 — DESIGN CHOICE

Monolith vs Modular System

A single script is faster to start. A modular system is easier to trust.

One Giant Script

Fast to build, hard to debug. Everything is tangled together. If the system places a bad trade, you may not know whether the issue came from data, signal logic, sizing, execution, or risk.


Good for a toy example. Dangerous as complexity grows.

Modular System

Slower to design, easier to maintain. Each component can be tested separately. You can replace the signal logic without rewriting execution. You can improve risk without touching data ingestion.


Good for systems you expect to keep alive.

For beginners, the lesson is not “build enterprise software from day one.” The lesson is to keep the roles separate in your head, even when the first version is small. A small repo can still have clean boundaries.

06 — BUILDER MAP

How This Maps to a Repo

The mini-company metaphor can become a folder structure. Not because folders are magic — because folders force clarity.

Example Starter Structure
/data
  fetch_prices.py
  validate_feed.py

/research
  indicators.py
  signals.py

/portfolio
  sizing.py
  exposure.py

/risk
  limits.py
  kill_switch.py

/execution
  broker_client.py
  orders.py
  reconciliation.py

/monitoring
  logs.py
  alerts.py

/backtests
  run_backtest.py
  reports.py

This is not the only possible structure. The point is the separation. Data code should be easy to find. Signal code should be separate from order placement. Risk checks should be visible, not hidden inside a random function. Logs and reports should be treated as part of the system, not an afterthought.

Clean architecture is not about looking professional.

It is about making mistakes easier to find before they become expensive.
07 — WHY PROS DO THIS

This Is How Serious Desks Think

Professional quant and trading systems are organized around roles because specialization reduces hidden risk.

A trading desk may have researchers, traders, execution specialists, portfolio managers, risk teams, compliance, and operations. Your personal algo does not need a full organization. But the same logic applies: the system should separate idea generation, order placement, capital allocation, and risk authority.

That separation makes the system testable. You can ask: is the data clean? Is the signal firing correctly? Is sizing behaving as expected? Did the broker actually receive the order? Did the risk layer approve it? Each question has a place to live.

↳ Architecture is how you stop “the algo did something weird” from becoming an unsolvable sentence.
08 — WHERE TO GO FROM HERE

The API Turns the Map Into a Playground

Once the structure is clear, the next step is building small examples that connect to real market data and broker workflows.

This is where the EFG API matters. The articles explain the concepts. The repos should eventually show small working examples: fetching data, generating a signal, running a backtest, paper-trading a simple rule, placing controlled orders, and enforcing risk limits.

That repo layer is where students and builders can experiment. The article stays clean and conceptual. The code becomes a living thing that can be updated, debugged, improved, and forked.

The article explains the concept.
The repo shows the working example.

Together, they turn the stock market into a builder playground.

One final boundary matters: building your own tools to understand and trade your own account is one thing. Offering automated trading services to others is a different conversation. That brings regulatory, operational, and responsibility questions that sit outside this beginner track.

09 — SUMMARY

What You Should Now Understand

Six things to carry into the final part.

Key Takeaways — Part 06
  • A serious algo should not be one giant script. It should have clear roles and boundaries.
  • The five core roles are Data Agent, Research Agent, Execution Agent, Portfolio Manager, and Risk Officer.
  • The Risk Officer must outrank the strategy. If risk says stop, the system stops.
  • Clean architecture makes the system easier to test, debug, monitor, and improve.
  • A repo structure can mirror the architecture: data, research, portfolio, risk, execution, monitoring, and backtests.
  • The article explains the concept; the repo should eventually show the working example.
